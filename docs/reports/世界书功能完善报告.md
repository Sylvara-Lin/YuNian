# 世界书（Worldbook/Lorebook）功能完善报告

> 参考标准：社区通用世界书实现
> 克隆位置：社区公开实现（供后续查阅）

## 一、参考项目研究结论

世界书由三部分组成：

| 部分 | 位置 | 要点 |
|---|---|---|
| 数据模型 | `data/model/Assistant.kt` | `Lorebook` = 名称+描述+启用+条目列表；条目 `RegexInjection` 含 keywords/useRegex/caseSensitive/scanDepth/constantActive/priority/injectionPosition(5种)/injectDepth/role(USER/ASSISTANT) |
| 注入逻辑 | `data/ai/transformers/PromptInjectionTransformer.kt` | 取最近 scanDepth 条非系统消息拼接上下文 → 每条目**只判断一次**是否触发 → 按优先级排序、按位置分组 → BEFORE/AFTER_SYSTEM_PROMPT **合并进系统提示词文本**，其余位置按 role 生成 user/assistant 合并消息 → AT_DEPTH 按深度降序插入 → safe insert 避开工具调用链 |
| 编辑 UI | `ui/pages/extensions/PromptPage.kt` | 卡片列表 + ModalBottomSheet 编辑（全字段表单）+ 关键词 chips + 常驻/正则/大小写开关 + 保存校验（有关键词或常驻才可保存） |

## 二、YuNian 现状诊断（3 个问题的根因）

### 问题 1：功能整体不完整
- `feature/worldbook` 模块只有 Repository，无 ViewModel/UI；实际 UI 挂在 `feature/settings` 里且功能极简
- 列表页：无删除、无启用开关、无条目数
- 详情页：条目无编辑/删除/启停入口

### 问题 2：内容提示（prompt）不完整、生成效果不理想
- 注入内容带 `[Lorebook: 3 - Triggered by: "xx"]` 元数据 header 和 `[Worldbook Injections]` 包装 → 污染提示词，模型把内部元数据当正文读
- 所有注入一律以 `system` 角色插入 → 条目配置的 USER/ASSISTANT 角色完全无效
- BEFORE/AFTER_SYSTEM_PROMPT 插入独立 system 消息而非并入系统提示词 → 部分 API 对多条 system 支持差
- 同一条目在多条消息命中关键词会**重复注入多次**
- AT_DEPTH 多个不同深度的条目被压成最小深度一次注入
- 不支持正则关键词匹配

### 问题 3：编辑过程异常（加载/修改/保存/回显报错）
- **致命 bug**：新建条目时 `lorebookId` 硬编码为 `0`，没传当前世界书 ID → 条目全部存成孤立数据，详情页加载不到（回显为空），注入也永远查不到（"保存了却不生效"的直接原因）
- `getLorebookWithEntries` 只返回 enabled=1 的条目 → 停用条目在编辑页凭空消失，无法重新启用

### 迁移二次核查（针对"确定做好了吗"的硬验证）

用 SQLite 真实模拟迁移（`_verify_migration.py`，保留在工作区可复跑），三条升级路径全部 PASS：

| 场景 | 迁移动作 | 结果 |
|---|---|---|
| A. 标准 v41 老库（无 useRegex 列） | ALTER 加列 | PASS，迁移后与 42.json 逐列一致 |
| B. 半成品期构建的 v41 库（已带 useRegex） | 幂等跳过 | PASS |
| C. 全新安装 v42 | 直接建表 | PASS |

**核查中发现的事实**：`41.json` 基线已被更早的并行会话污染（其 `lorebook_entries` 混入了 useRegex——当时实体加列后回退不彻底被 KSP 覆盖导出）。这不影响运行时（Room 升级校验只用目标版本 42.json），且 41.json 与 42.json 的 identityHash 完全相同（`8f06c9a8...`），证明历史构建与当前构建的 schema bundle 一致——**不存在打开旧库时 "Room cannot verify the data integrity" 闪退的风险**。上次正式打包的 KSP 生成物（`build/generated/ksp/release/.../AppDatabase_Impl.kt`）显示打包时实体已含 useRegex，即现役设备库可能已带此列——`addColumnIfMissing` 的幂等设计恰好覆盖该分叉。

## 五、行为对照（修复前 → 修复后）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 新建条目 | 存到 lorebookId=0，列表/注入均不可见 | 挂到当前世界书，立即可见可注入 |
| 编辑已存条目 | 无入口 | 卡片铅笔按钮，双模式表单回显全字段 |
| 停用条目 | 从编辑页消失 | 仍显示（带"已停用"标记），可重新启用 |
| 注入内容 | 带 `[Lorebook:..Triggered by..]` 噪声 | 纯条目内容 |
| 角色配置 | 全部按 system 注入 | 按 user/assistant 注入，同角色合并 |
| 同条目多次命中 | 重复注入 N 次 | 只注入一次 |
| 正则关键词 | 不支持 | 支持（带大小写开关） |
| 删除世界书/条目 | 无入口 | 均有删除按钮 + 确认弹窗 |
