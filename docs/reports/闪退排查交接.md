## 一、现象

正式版 APK（thin-shell 加壳 159MB / plain 110MB 均复现）安装后**点图标即闪退**，约启动后 2.8 秒进程被杀（"crashed too many times"）。

## 二、已确认的硬事实（别再重复排查）

### 1. 崩溃点（native，非 Java）
- 线程：`RenderThread`（tid 6492 / 12659）
- 信号：`Fatal signal 11 (SIGSEGV), code 2 (SEGV_ACCERR)`
- debuggerd 判定：`Cause: stack pointer is not in a rw map; likely due to stack overflow` —— **栈溢出**
- backtrace：512+ 帧**全部是同一对函数交替递归**：
  `libhwui.so RenderNode::prepareTreeImpl ↔ SkiaDisplayList::prepareListAndChildren`（见 tombstone）
  → 含义：**hwui 在 prepare 阶段递归遍历渲染树时无限下钻** = View/RenderNode 树存在**环或超深嵌套**。
- 崩溃前 ~0.5s 系统日志出现 `blurUtils, initBackgroundBlurMinInterval`（窗口背景模糊初始化）。
- 启动过程内存 RSS 559→687MB 反复波动，GC 频繁。

### 2. 关键对照实验：**与加壳无关！**
- 加壳版（159MB app-release.apk）：崩
- **同代码无壳版（110MB app-release-plain.apk）：同样崩**（同样的 RenderThread 栈溢出，tombstone_00）
- → 是**业务代码/UI 代码**问题，不是 thin-shell / dex2c / 签名问题。打包链路本身是好的（见 `打包交接说明.md`）。

## 三、怀疑方向（按可能性排序，未验证）

### ① 液态玻璃 drawBackdrop 自嵌套（最可疑）
最近把玻璃组件改成"真液态玻璃"，用了 **Kyant AndroidLiquidGlass 的 `drawBackdrop` + `vibrancy()`**：
- `core/ui-common/.../component/glass/GlassButton.kt:58`（`Modifier.drawBackdrop(... vibrancy())`）
- `core/ui-common/.../component/glass/LiquidBottomTabs.kt:292/350/484`（3 处 drawBackdrop）

崩溃在首帧显示后 ~1.3s（05.95 setContent → 07.29 崩），且栈是 prepare 递归 170+ 层——**特征像"每帧给渲染树包一层 backdrop/捕获层"**（170 帧 ≈ 170 层），或 backdrop 捕获链把窗口内容当成自己的背景形成环。加上崩溃前系统正好初始化背景模糊，嫌疑很大。

排查动作建议：
1. 看 `MainScreen`/首页是否用 `LiquidBottomTabs`/`GlassButton`（大概率用了）。
2. **最快验证**：临时把上述 drawBackdrop 调用换成普通模糊/纯色（或按 `HardwareInfo.tier == LOW` 降级路径强制走），打 plain 包装机测，崩不崩立见分晓。
3. 若确认：查 Kyant backdrop 在 Compose 里的 backdrop 捕获实现（gradle 缓存里 kyant-backdrop aar），看它是否往 window/decorView 挂捕获层、是否每帧 addView。

### ② 某个 Composable 无限重组/每帧加节点
栈深 ≈ 帧数（2.8s×60fps≈168 帧 vs 树深 ~170 层）高度巧合，也可能是某 `LaunchedEffect`/动画里循环把内容包进新层级。搜索主界面路径中 post/withFrameNanos/无限循环里包 View 的代码。

### ③ 已排除项（别浪费时间）
- ❌ 加壳/壳解密（plain 同崩）
- ❌ dex2c（0 方法桩）
- ❌ 病娇模式 YandereModeManager（纯数据逻辑，无 View 操作，已通读）
- ❌ 签名/keystore
- 注意：日志里 `NativeBridge.wbAesObfuscateTables No implementation found` + `CoreComponentFactory not found` 是**噪音**（被 catch 的降级），不是崩溃源。

## 五、建议的下一步（给接手 AI 的行动顺序）

1. **先做怀疑①的二分验证**（改 drawBackdrop → 普通效果，打 plain 包，装手机测）。改动小、验证快，是当前最高性价比动作。
2. 若 ① 排除，用 `adb shell am start` 后**立刻连续 dumpsys activity top**（崩前 ~1.3s 窗口，循环抓）试图抓 View 层级，看是不是某棵树每帧 +1 层。
3. 复现时可在 manifest 开 `android:debuggable` 的 debug 包上抓 Java 侧堆栈辅助定位。
4. 修复后按 `打包交接说明.md` 的已验证命令出完整加壳包，装机确认不闪退再交付。
