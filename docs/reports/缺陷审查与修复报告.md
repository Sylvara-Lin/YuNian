## 二、本轮已执行的修复

### 修复 1（P0）：启动期原生崩溃 — `StaticApkShell`

**根因**：`app/src/main/java/com/yunian/ai/security/StaticApkShell.kt` 是 Gradle 正常构建（debug/普通 release）时的真正 Application 入口（由 `src/main/AndroidManifest.xml` 与 `src/shell/AndroidManifest.xml` 的 `android:name=".security.StaticApkShell"` 注册）。其 `init` 块吞掉了 `System.loadLibrary("lianyu_shell")` 的失败，但紧接着的 `attachBaseContext()` 仍**无条件**调用三个 `external` 方法：

```kotlin
nativeAntiHookInit()          // 无 try/catch
nativeEnableMemoryGuard()     // 无 try/catch
nativeShellInitWithBlob(...)  // 部分包裹
```

当 `liblianyu_shell.so` 缺失、ABI 不匹配或加载失败时，调用 `external` 方法会抛 **`UnsatisfiedLinkError`（`Error`，非 `Exception`，`try/catch(Exception)` 拦不住）**，进程在 attach 阶段直接闪退。这正是"多数设备闪退"的最主要根因。对照 Java 薄壳版 `app/src/shell/java/.../StaticApkShell.java`（每个步骤都 `try/catch(Throwable)`），Kotlin 版存在明显的防护缺失。

**修复**：重写 `attachBaseContext()`，引入 `shellLibAvailable` 标志，所有原生调用与反射类加载均用 `runCatching` / `try/catch` 兜底，加载失败降级为"跳过安全加固、业务正常启动"，与 Java 薄壳行为对齐。

**文件**：`app/src/main/java/com/yunian/ai/security/StaticApkShell.kt`

### 修复 2（P0）：初始化异常导致主界面永久卡死

**根因**：`app/src/main/java/com/yunian/ai/YuNianApplication.kt` 的 `initBusiness()` 中，`ServiceRegistry.markInitialized()` 位于 `bgScope.launch { ... }` 内部，且前面的 `registerServiceProviders(app)`、`seedDefaultCompanion(app)` **未被 try/catch 包裹**。一旦注册阶段抛异常，`markInitialized()` 永远不会执行 → `MainActivity` 中 `!isServiceReady` 分支一直显示 `CircularProgressIndicator`，App 表现为"启动即白屏转圈/无法进入主界面"。

**修复**：用 `try { ... } catch (CancellationException) { throw } catch (Exception) { log } finally { ServiceRegistry.markInitialized() }` 保证初始化状态**最终必然置位**，异常仅记录日志不阻断 UI。

**文件**：`app/src/main/java/com/yunian/ai/YuNianApplication.kt`（`initBusiness`）

### 修复 3：全仓 AI 风格注释清理

**根因**：源码中大量"AI 味"注释——逐行叙事性注释、`──` 分段线、`Step 1/2/3`、emoji、以及 `MainRoute.kt` 中"控制论：离散系统差分方程"这类堆砌术语的 KDoc，导致代码一眼即被识别为 AI 生成。

**处理**：新增 `tools/strip_comments.py`，用状态机正确识别并剥离行注释 `//`、块注释 `/* */`、KDoc `/** */`，**并跳过字符串、字符、三引号原始字符串字面量**（已单独验证 `"https://x//y"`、`"https?://[\\w./?=&%-]+"` 正则、`"image/*"` MIME 等均完整保留）。

**结果**：`658/691` 个 Kotlin/Java 文件被处理，共移除约 **406,244 字符**注释；处理后的字符串/正则/URL 无一处损坏。

### 修复 4（P1）：病娇模式实际不生效

**现象**：开启「病娇模式」后，对话中从不出现病娇式回应，模式形同虚设。

**根因**（按影响排序）：

1. **缺失 `<queries>`（主因）**：`app/src/main/AndroidManifest.xml` 未声明 `<queries>`。Android 11（API 30）起启用包可见性过滤，`PackageManager.getInstalledApplications(0)` 在未声明查询意图时**只会返回本应用自身**，导致 `collectInstalledApps()` 拿到的 `installedApps` 恒为空。
2. **提示词生成早退**：`buildYandereModeSystemPrompt()` 在 `usageApps.isEmpty() && installedApps.isEmpty()` 时直接 `return ""`。usage-stats 权限需用户在系统设置手动授权（默认未授），于是 `usageApps` 也常为空 → 两个列表都空 → 永远返回空串 → `appendYanderePromptIfNeeded` 判定 `isBlank()` 后直接放弃拼接。
3. **触发门槛过苛刻**：`shouldTriggerThisRound()` 每 5 轮冷却 + 每次仅 30% 概率，即便有数据也极少触发，难以被用户观察到。
4. **空缓存不刷新**：`requestRefresh()` 对「未过期但内容为空」的缓存会直接 `return`（此前 `<queries>` 缺失已写入了空缓存），导致修复后若不清缓存仍不生效。

**修复**：

- `app/src/main/AndroidManifest.xml`：新增 `<queries>`（`MAIN`/`LAUNCHER` 意图），使 `getInstalledApplications()` 能返回真实的第三方应用。
- `core/common/.../YandereModeManager.kt`：
  - `collectInstalledApps()` 额外过滤掉自身包名（`it.packageName != appContext.packageName`）。
  - `requestRefresh()` 新增「空缓存即视为过期」判断，空缓存不再被 6h TTL 拦截。
  - `shouldTriggerThisRound()` 改为**数据感知**：无可用数据时不消耗触发轮次；冷却间隔由 5 降至 3、触发概率由 0.3 提至 0.5（新增 `TRIGGER_PROBABILITY` 常量），仍保留"不要每轮都提"的克制。
  - 新增 `hasUsableData()`：`installedApps` 或 `usageApps` 任一非空即视为有数据。
  - `buildYandereModeSystemPrompt()` 在无 usage-stats 时回退输出「设备上安装的部分应用」列表（取前 20 个），使病娇即便没有使用时长权限也有具体素材可"吃醋/关心"。

**涉及字段/配置**：无数据结构变更，`CacheSnapshot` / `InstalledApp` / `UsageApp` 保持不变；DataStore 键 `yandere_mode_enabled` / `yandere_mode_usage_stats` / `yandere_mode_installed_apps` 不变。

**文件**：`app/src/main/AndroidManifest.xml`、`core/common/src/main/java/com/yunian/ai/common/YandereModeManager.kt`

## 三、缺陷分级清单（含未修复项）

### P1 — 设备兼容 / 功能缺失（需决策后修复）

#### P1-1：ABI 仅 arm64-v8a，与"多设备适配"目标冲突

- **根因**：`app/build.gradle.kts` 中 `ndk { abiFilters += listOf("arm64-v8a") }` 将 APK 锁定为 64 位 ARM；而 `core/security` 模块声明了 4 个 ABI、`app/src/main/jniLibs/` 又混有 armeabi-v7a/x86/x86_64 的库，口径不一致。
- **影响**：32 位设备（armeabi-v7a）与 x86 模拟器**无法安装**；`libLiteRt.so`、`liblitertlm_jni.so`（本地大模型 LiteRT-LM）仅在 arm64-v8a/x86_64 存在，armeabi-v7a/x86 缺失，一旦放开 ABI 会立即触发本地模型 `UnsatisfiedLinkError`。
  > **修订（2026-09-17）**：`feature:localmodel` 已退役，LiteRT-LM 全部 `.so` 与配套声明已从仓库删除，本条中与 LiteRT 相关的部分不再适用；`abiFilters` 仅 arm64-v8a 为仓库既有设计。
- **方案**：若需覆盖 32 位设备，需先补齐 onnx/安全 shell 的全 ABI `.so`，再统一 `abiFilters` 与 `core/security` 的 `Application.mk` 口径；否则建议在 `build.gradle.kts` 中显式注释/文档说明"仅支持 arm64"，避免后续误改。
- **文件**：`app/build.gradle.kts:41-43`、`core/security/build.gradle.kts:15-17`、`core/security/src/main/cpp/Application.mk:1`、`app/src/main/jniLibs/`

#### P1-2：`error()` 用异常做控制流，边界场景脆弱

- **根因**：多处用 Kotlin `error()`（抛 `IllegalStateException`）表达业务失败，而非返回值/领域异常。
- **影响**：如 `WeChatIdentityMapPortImpl.kt:66` 在伴侣被删除后仍尝试绑定时 `error("companion not found")`（当前被 `WeChatViewModel` 的 `runCatching` 接住转为 UI 事件，暂不崩溃，但属脆弱耦合）；`SdkWeChatTransport.kt` 未登录时 `error("未登录微信")`；`ChatMessageCrypto.kt:130/152` 密钥不可用时 `error(...)`。
- **方案**：将 `bind` 改为返回 `Boolean`/领域结果类型；密钥缺失时降级为非加密/重建密钥而非抛异常。
- **文件**：`app/src/main/java/com/yunian/ai/wechat/WeChatIdentityMapPortImpl.kt`、`feature/wechat/src/main/java/com/yunian/ai/feature/wechat/data/SdkWeChatTransport.kt`、`core/database/src/main/java/com/yunian/ai/database/repository/ChatMessageCrypto.kt`

#### P1-3：重复的 `WorkManager.initialize()` 调用

- **根因**：`YuNianApplication` 已实现 `androidx.work.Configuration.Provider`，但 `MainActivity.onCreate` 第 79 行仍显式 `WorkManager.initialize(...)`；Java 薄壳 `StaticApkShell.java` 也反射式初始化一次。多入口重复初始化，易在冷启动竞态下触发 `IllegalStateException: WorkManager is already initialized`（已被 try/catch 吞掉，但属隐患）。
- **方案**：统一由 `Configuration.Provider` 提供配置，删除 `MainActivity` 中的手动初始化。
- **文件**：`app/src/main/java/com/yunian/ai/MainActivity.kt:79`

### P2 — 可维护性 / 代码整洁

#### P2-1：壳层（Shell）双实现严重分叉

- **根因**：生产入口存在两套 `StaticApkShell`：Kotlin 版（`app/src/main/java/.../StaticApkShell.kt`，Gradle 直出）与纯 Java 版（`app/src/shell/java/.../StaticApkShell.java`，`package_thin_shell.py` 打包）。两套声明的 `external` 方法签名**不一致**（Kotlin 用 `nativeAntiHookInit/nativeEnableMemoryGuard/nativeShellInitWithBlob`，Java 用 `nativeSetApkCert/nativeDecryptDex/...`），`Android.mk` 的导出符号表只对齐了 Java 版。任何一侧改动都极易失同步，是本次闪退的深层诱因。
- **方案**：抽出一个共享的"原生接口清单"，两侧强制对齐；或删除已弃用的 Kotlin 壳路径，统一走单一壳。
- **文件**：`app/src/main/java/com/yunian/ai/security/StaticApkShell.kt`、`app/src/shell/java/com/yunian/ai/security/StaticApkShell.java`、`core/security/src/main/cpp/Android.mk`

#### P2-2：废弃/空实现类残留

- `app/src/main/java/com/yunian/ai/security/YuNianShellApplication.kt`（`@Deprecated`，已不注册）
- `OnePieceShellGate`（`recordStartupPreflight`/`verifyBeforePayload` 均为空实现）
- `SActivity.kt` 仅做转发，`MethodRecoveryEngine.loadClassBytes` 恒返回 null 的 stub。
- **方案**：确认无引用后删除，减少误读与维护面。

#### P2-3：仓库根目录杂物文件

- `_encode_url.py`、`_fix_navgraph.py`、`create_regex.py`（临时脚本）、`nul`（Windows 重定向产物）、`debug-voice-call-crash.md` 等散落根目录。
- **方案**：移入 `tools/` 或删除；`nul` 应直接删除。

#### P2-4：`SecurityGuard` 悬空的 `private` 修饰符与孤儿 KDoc

- `core/security/src/main/java/com/yunian/ai/security/SecurityGuard.kt` 原第 343-351 行存在 `private` 后接孤立的"Run the complete detection chain" KDoc，再接 `fun isEmulatorBySensors()` 的畸形结构（`private` 实际修饰的是后面的函数，但中间隔了无关注释），属明显的手工合并残留。注释剥离后结构已清晰，建议顺手将 `private` 与其函数合并到同一行。

#### P2-5：`onTerminate()` 清理逻辑在 Android 上不可达

- `YuNianApplication.onTerminate()` 中 `ServiceRegistry.clear()` 等清理，在真实设备上 `onTerminate()` 几乎不会被系统调用（仅模拟器特定场景），属死代码。
- **方案**：将清理迁移到 `onTrimMemory(TRIM_MEMORY_UI_HIDDEN)` 或进程退出兜底，或直接删除误导性注释。
