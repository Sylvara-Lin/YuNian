第一区 · 项目心智模型（v2 插件架构视角）

0. 架构范式：万物皆插件（Agent = Model + Harness）

本项目已演进为「万物皆插件」架构，参考 DeepSeek Harness（dsh）工程范式：底层是 Cordis 插件/服务内核，插件/服务经内核注册、通过声明的契约（接口/扩展点）与依赖注入被发现和调用，可通过服务注册表、事件总线/钩子横向协作。这种"由容器管理的服务依赖"是解耦的正常设计，不等于旧报告所说的"违反单向依赖"。

关键论断（DeepSeek Harness 官方）："Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself. There is no privileged core to patch."

2. 插件契约与"为什么横向协作不违反解耦原则"

Cordis 核心机制（已在本项目完整落地）：

  • 服务依赖声明（inject / requires）：插件在 LianYuPlugin.requires 声明需要的框架服务键（如 PluginServices.AGENT），PluginHostImpl.load 在 setup 之前 fail-closed 校验。load order 由依赖图算出，不需要手动编排启动顺序。
  • 服务注入（ctx.provide / inject）：每个服务在 Context 上占据稳定键位（如 ctx.tools / ctx.channels / ctx.agent），插件按 key 找服务而不 import 具体实现。消费方代码一行不用改，提供方可以热替换。
  • 类型化事件（5 种派发模式）：emit（同步广播）/ parallel（并发等待）/ serial（顺序 bail）/ bail（同步 serial）/ waterfall（中间件链）。多个互不相识的插件组成一条决策链，不共享服务也能通信。
  • 可逆副作用（ctx.effect）：每个注册返回 disposer，插件卸载时按 LIFO 回滚。服务消失时依赖它的插件自动卸载（Cordis「卸载不留鸡毛」）。
  • 宿主级共享事件总线：同一宿主装载的全部插件共用一张监听表，A 的 emit 能被 B 的 on 收到；查询期活性兜底（卸载后适配器随之消失）。

结论：插件经内核注册、通过声明的契约与依赖注入被发现和调用、通过服务注册表/事件总线横向协作，这是解耦的正常设计，不是"违反单向依赖"。任何 feature 模块代码出现在 core:agent 的引用列表（如 AgentDialogueCoordinator 调 ToolRegistry.availableTools()），都是 Service Registry 模式而非反向依赖违规。

判定：维持（致命）

// onTaskRemoved 新增
override fun onTaskRemoved(rootIntent: Intent?) {
    super.onTaskRemoved(rootIntent)
    runCatching {
        if (QQBotServiceLocator.tokenStore(applicationContext).hasAccount()) {
            scheduleRestartWithDebounce()
        }
    }
}

// scheduleRestartWithDebounce 新增（类内私有方法）
private fun scheduleRestartWithDebounce() {
    val now = System.currentTimeMillis()
    if (now - lastRestartAtMs < RESTART_DEBOUNCE_MS) {
        Log.w(TAG, "Restart debounced (last=${now - lastRestartAtMs}ms ago)")
        return
    }
    lastRestartAtMs = now
    start(applicationContext)
    runCatching {
        val request = OneTimeWorkRequestBuilder<QQBotRestartWorker>()
            .setInitialDelay(30, java.util.concurrent.TimeUnit.SECONDS)
            .build()
        WorkManager.getInstance(applicationContext).enqueueUniqueWork(
            QQBotRestartWorker.UNIQUE_WORK_NAME,
            ExistingWorkPolicy.REPLACE,
            request,
        )
    }.onFailure { Log.w(TAG, "schedule restart worker failed: ${it.message}") }
}

// companion object 内新增常量
private const val RESTART_DEBOUNCE_MS = 10_000L

private fun startHeartbeat(intervalMs: Long) {
    heartbeatJob?.cancel()
    heartbeatActive = true
    lastHeartbeatAckMs = 0L
    heartbeatAckTracker.reset()
    heartbeatJob = scope.launch {
        val period = (intervalMs * 0.8).toLong().coerceAtLeast(5000)
        // Hello 后立即首发：协议约定 + AGENTS.md 教训 #1
        // 首发前调 onBeforeSend：pendingSentAtMs=0 走 else 分支只记基线，与循环内语义对齐
        if (heartbeatAckTracker.onBeforeSend(System.currentTimeMillis(), lastHeartbeatAckMs)) {
            reconnect()
            return@launch
        }
        send(json.encodeToString(QQGatewayPayload(op = opHeartbeat, d = JsonPrimitive(lastSequence.get()))))

        while (isActive && heartbeatActive) {
            delay(period)
            if (!heartbeatActive) break
            if (heartbeatAckTracker.onBeforeSend(System.currentTimeMillis(), lastHeartbeatAckMs)) {
                SecureLog.w(TAG, "No heartbeat ACK for 2 consecutive intervals, reconnecting")
                reconnect()
                return@launch
            }
            send(json.encodeToString(QQGatewayPayload(op = opHeartbeat, d = JsonPrimitive(lastSequence.get()))))
        }
    }
}

package com.yunian.ai.feature.notification

import android.content.BroadcastReceiver
import android.content.Context
import android.content.Intent
import androidx.work.ExistingWorkPolicy
import androidx.work.OneTimeWorkRequestBuilder
import androidx.work.OutOfQuotaPolicy
import androidx.work.WorkManager
import com.yunian.ai.common.SecureLog
import com.yunian.ai.common.concurrent.AppDispatchers
import kotlinx.coroutines.CoroutineScope
import kotlinx.coroutines.launch

class BootReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        if (intent.action != Intent.ACTION_BOOT_COMPLETED) return
        // goAsync + IO 协程：主线程立即返回，无 ANR；与 WeChatBootReceiver 模式对齐
        val pendingResult = goAsync()
        CoroutineScope(AppDispatchers.io).launch {
            try {
                // 直接尝试 FGS（Android 12+ BOOT_COMPLETED 在白名单内；OEM 可能收紧）
                runCatching { CompanionKeepAliveService.start(context) }
                    .onFailure { SecureLog.w("BootReceiver", "FGS start failed: ${it.message}") }
                // 幂等兜底：FGS.start 内部 catch，外层无法感知失败；重复 startForegroundService 系统层去重无副作用
                runCatching {
                    val request = OneTimeWorkRequestBuilder<BootFallbackWorker>()
                        .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
                        .build()
                    WorkManager.getInstance(context.applicationContext).enqueueUniqueWork(
                        BootFallbackWorker.UNIQUE_WORK_NAME,
                        ExistingWorkPolicy.REPLACE,
                        request,
                    )
                }.onFailure { SecureLog.w("BootReceiver", "fallback worker enqueue failed: ${it.message}") }
                CompanionMessageWorker.schedule(context)
            } finally {
                try { pendingResult.finish() } catch (_: Exception) {}
            }
        }
    }
}

确认结果（v2.1）

判定：确认存在但不修

关键证据（agent-native/src/retry.rs:33-53）：

  • max_backoff = 8s（单次退避硬上限，同时约束 Retry-After）
  • total_budget = 30s（整个重试序列绝对上限，含睡+请求）
  • max_attempts = 3（首次 + 最多 2 次重试）
  • initial_backoff = 800ms，×2 指数退避

用户取消时的实际滞后：

  • 最坏情况：首次请求失败 → 800ms 退避期间取消 → 滞后 ≤ 800ms
  • 次坏情况：第二次重试失败 → 1600ms 退避期间取消 → 滞后 ≤ 1600ms
  • 极端情况：第三次重试失败 → 3200ms 退避期间取消（受 max_backoff=8s 封顶）→ 滞后 ≤ 3200ms
